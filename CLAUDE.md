# nym-maestro

## Overview
Python mTLS orchestrator für ein 22-Node Nym Exit-Gateway Fleet. Zwei Komponenten: ein zentraler Orchestrator (Control Plane) und ein Agent, der auf jedem Node läuft (Data Plane).

## Architecture
- **Orchestrator** (Control Plane): FastAPI-App, läuft lokal auf `localhost:7766`. Aggregiert Fleet-State, liefert die Dashboard-UI aus, spricht die Agents an.
- **Agent** (Data Plane): stdlib-only Python, deployed auf jedem der 22 Nodes, lauscht auf Port 8443 über mTLS. Keine Third-Party-Dependencies — Agent muss ohne Paketmanager/venv-Setup auf frisch provisionierten Nodes laufen.
- **Storage**: SQLite orchestrator-seitig für aggregierten State. Agent puffert lokal (30-Tage Rolling History) und meldet nach oben.
- **Traffic/Throughput-Modell**: Three-Plane-Visualisierung — On-Wire Sphinx (Mixnet-Paketebene), Exit Payload (entschlüsselter/austretender Traffic), Physical Uplink (rohe NIC-Counter). Pro-Node-Detailkarten im Dashboard trennen WireGuard- und Mixnet-Metriken separat aus.

## Non-negotiable constraints
- **Agent-Code bleibt stdlib-only.** Niemals Third-Party-Deps auf Agent-Seite einführen — der ganze Sinn ist Deployment auf 22 Nodes ohne Package-Management-Overhead.
- Orchestrator-Seite darf FastAPI/uvicorn/etc. nutzen, das ist unkritisch.
- mTLS ist die Vertrauensgrenze zwischen Orchestrator und Agents auf Port 8443. Änderungen an Cert-Handling, mTLS-Handshake oder Agent-Auth explizit ankündigen, nicht "nebenbei" mitrefactoren.

## Data model
- SQLite orchestrator-seitig für aggregierten Fleet-State.
- Agent-seitig: 30-Tage Rolling History Buffer (zuletzt hinzugefügt — bei allem, was History/Retention betrifft, hier zuerst nachsehen).
- Disk-Usage-Spalte kürzlich ergänzt, vermutlich neben den übrigen Per-Node-Metriken (WireGuard-, Mixnet-Counter).

## UI / Dashboard
- Pro-Node-Detailkarten: getrennte WireGuard- und Mixnet-Sektionen.
- Bekannter kürzlich behobener Bug: Modal-z-index-Problem — bei Änderungen an Modals/Overlays auf Stacking-Context-Regressionen prüfen.
- Favicon kürzlich ergänzt — trivial, aber der Vollständigkeit halber vermerkt.
- Modal-Konventionen (verifiziert): `div.overlay` als Sibling von `.wrap`, `classList.add/remove('open')`, `.overlay` z-index 20, `.overlay.overlay-top` z-index 40 für Modals, die über einem offenen Modal liegen (Results/Throughput). Neue Overlays IMMER in beiden Listen am Script-Ende registrieren (Backdrop-Click + Escape) — `eb-overlay` fehlt in beiden, das ist ein bestehender Bug, nicht das Muster.
- Fetch-Helper ist `api(path, opts)`; Fehler via `toast(e.message, true)`; Per-Node-Ergebnisse via `showResults(title, r.results)` → `buildResultCards()`. Neue Result-Felder werden dort ergänzt; `res.kind` unterscheidet Shapes (sonst kollidieren gleichnamige Felder wie `verified` zwischen Features).

## Landing page (public node overview)
- Jede Exit-Gateway serviert unter `/var/www/<hostname>/index.html` eine öffentliche Notice-Page mit Legal-T&C. Der Node-Overview-Block darin wird von maestro generiert (Ersatz für das tote nymesis-iframe) — Zweck: eine vollständige, eindeutige IP-Liste für Behörden.
- `landing.py` (orchestrator-seitig, stdlib-only) ist der Generator: Whitelist, Validierung, Rendering, Splice, Diff. Splice passiert zwischen `<!-- NODES:AUTO START/END -->`; beim ersten Lauf wird der alte handgeschriebene Abschnitt via `LEGACY_RE` ersetzt. Alles außerhalb der Marker (T&C, SVG) bleibt unberührt.
- **Whitelist nie erweitern:** nur `name`, `ip`, `hostname`, `cc` verlassen maestro. Hart kodiert in `select()`, damit neue Admin-Felder nicht leaken können. Insbesondere ist `node_id` **kein** Fallback für einen leeren `name` (interne IDs gehören nicht auf eine öffentliche Seite) — Fallback ist der Hostname, plus Warnung.
- **Sicherheits-Invarianten (jeweils durch einen Regressionstest in `test_landing.py` abgedeckt — nicht "aufräumen"):**
  - Der Manifest-JSON im HTML-Kommentar escaped **jeden** `-` als `-`. Nicht auf `replace("--", <guard>)` zurückbauen: `str.replace` ist non-overlapping, `"--->"` wurde zu `"-<guard>-->"` und schloss den Kommentar → ein Node-Name wie `AT01---><img onerror=...>` brachte lebendes Markup auf die öffentliche Seite. **Die mitgelieferte Referenz `generate_landing.py` hat diesen Bug ebenfalls.**
  - `is_exit_gateway()`: der Selbstbericht des Nodes gewinnt in beide Richtungen; `exit: False` wird nie publiziert, egal wie der Node heißt. Ohne `status` entscheiden Namens-Hints (ein Mixnode mit totem Agent wird also nicht gelistet).
  - Agent: Backups nie mit `shutil.copy2` — das öffnet das Ziel mit `'wb'` und schreibt durch einen dort platzierten Symlink (Root-Write überall hin). Stattdessen `_landing_copy_nofollow()` mit `O_NOFOLLOW`. Symlinks als `index.html` oder als Backup werden abgelehnt (`reason: "symlink"`), und ein Backup muss die Version tragen, die sein Name behauptet (sonst wäre `/etc/shadow` als `index.html.bak-aaaaaa` publizierbar).
  - Der Idempotenz-Skip vergleicht die **sha256 der ganzen Datei**, nicht den Versionsmarker. Der Marker hasht nur die Node-Liste, eine T&C-Änderung lässt ihn unverändert — ein Skip darauf hätte genau die wichtigste Änderung still verschluckt.
  - `/api/landing/preview` liefert `Content-Security-Policy: sandbox allow-scripts`. Der Master ist Fremd-HTML (gefetcht/eingefügt) und diese Origin hält das Dashboard-Cookie.
- Master liegt unter `~/.nym-maestro/landing/master.html` (Env: `MAESTRO_LANDING_DIR`), Deploy-Kopie unter `serve/index.html` + `.sha256`.
- Zwei getrennte Schritte im UI (Rebuild / Deploy) — bewusst, damit ein fehlgeschlagener Deploy ohne Neu-Generieren wiederholbar ist. Rebuild publiziert nichts.
- Die Seite ist statisch (funktioniert ohne JS) — `/api/nodes` ist localhost-only und ohne CORS, die Daten müssen also zur Build-Zeit eingebacken werden. Kein Live-Online-Status auf der Seite; das `list generated <date>` ist das Freshness-Signal.
- Agent-Actions: `landing_status`, `landing_deploy`, `landing_revert`. Deploy verifiziert sha256 vor jedem Disk-Zugriff, verlangt einen `NODES:VERSION`-Marker im Content, legt Backup `index.html.bak-<version>` an und swappt atomar. Webroot wird nie angelegt — fehlender Webroot/index.html wird gemeldet.
- Ein `index.html`, das ein Symlink ist, wird abgelehnt (`reason: "symlink"`): der Backup-Schritt würde sonst den Symlink-Zielinhalt ins web-servierte Verzeichnis kopieren.
- **Bekannte Einschränkung von `FQDN_RE`** (aus der Referenzimplementierung übernommen, in `landing.py` UND agent-seitig): Labels mit doppeltem Bindestrich werden abgelehnt — also auch Punycode/IDN (`xn--…`). Für die aktuellen `nym-exit-XX01.hermes-stakepool.de`-Hostnames irrelevant. Der Fehler ist fail-closed: Rebuild stoppt hart und nennt den betroffenen Node, statt ihn stillschweigend auszulassen. Wenn je ein IDN-Hostname dazukommt, muss das Pattern in beiden Dateien angepasst werden.

## Abuse replies
- Eigener Tab im Dashboard (Header-Nav `Nodes | Abuse replies`, Deep-Link `#abuse`; Node-Übersicht steckt in `#view-nodes`, der Tab in `#view-abuse`). Zweck: stringente, wiederholbare Antworten auf Abuse-Reports — gleicher Complainant (z.B. Paramount) bekommt wortgleich die letzte gespeicherte Antwort, nur mit neuer Case-ID.
- `abuse.py` (orchestrator-seitig, pure/stdlib, Suite `test_abuse.py`): Case-ID-/IP-Extraktion aus dem gepasteten Report, Complainant-Matching gegen bekannte Namen, Template-Rendering (`{case_id}`/`{ip}` via `str.replace`, nicht `format`), `swap_case_id` für den Reuse-Pfad. Kanon der Argumente steckt in `DEFAULT_TEMPLATE`: mere conduit · Inhalte werden nicht ausgewählt/verändert (bewusster Teil der Legal Strategy — Voraussetzung des Mere-Conduit-Safe-Harbour, nicht wegkürzen) · Betreiber-Statement „operated by Hermes Blockchain Ventures, fully complies with German and EU law" · no client data (differenziert nach Modus: Mixnet 5-hop vs. dVPN 2-hop — Abuse kommt i.d.R. über dVPN; Kernaussage: immer ≥2 getrennte Hops, Route wählt der Client aus unabhängigen Operators — „typically run by different, unrelated parties", NICHT „immer", da Entry+Exit theoretisch beide bei Hermes liegen können; Exit sieht nur den vorherigen Hop) · no logs · tight exit policy (Link auf die Nym-Exit-Policy) · rate limiting · we take this seriously.
- Draft-Logik (`POST /api/abuse/draft`): existiert ein früherer Case des Complainants ⇒ dessen Reply wird 1:1 wiederverwendet (Case-ID getauscht, Anrede via `swap_salutation` auf den aktuellen Provider umgeschrieben); sonst rendert das Template (editierbar via `GET/PUT /api/abuse/template`, gespeichert in `app_config`, leer = Reset auf Default). Reported IP wird gegen die Node-Registry gematcht (Node-Name). Adressat/Provider: UI-Override > im Report erkannter bekannter Provider (`guess_provider`) > letzter Case des Complainants — Anrede `Dear <Provider>,`, ohne Provider `Dear Sir or Madam,` (`{addressee}`-Platzhalter). Neue Provider einmal manuell eintragen; ab dann werden sie im Report erkannt.
- Storage: Tabelle `abuse_cases` (case_id, complainant = meldende Firma, provider = VPS-Hoster, node_name, ip, report_text, reply_text). CRUD unter `/api/abuse/cases`; `_ensure_columns` legt die Tabelle auf Bestands-DBs idempotent an.
- Nichts wird versendet — Replies sind Copy/Paste; Save persistiert Report+Reply für spätere Wiederverwendung. Paste in das Report-Feld triggert den Draft automatisch.

## NYX balance (ticket-redemption account)
- Jede nym-node hat einen eigenen Nyx-Account, dessen Balance die Ticket-Redemptions bezahlt. `nyx.py` (orchestrator-seitig, pure, Suite `test_nyx.py`): URL-Bau, Parsing von `auxiliary-details` (Adresse) und `/cosmos/bank/v1beta1/balances` (Summe aller `unym`-Einträge), `annotate()` für den Low-Verdict. Fetch in `app.py` (`refresh_nyx_all`, `_nyx_loop`, `POST /api/nyx/refresh`).
- Adresse kommt vom **öffentlichen** nym-node-HTTP-API `http://<ip>:8080/api/v2/auxiliary-details` (plain http, kein mTLS, nicht der Agent) — läuft also auch bei totem Agent. Balance über `wallet.NYX_REST_BASES` mit Fallback-Kette und `wallet.REST_UA` (stdlib-UA wird von den LCDs 403t).
- Storage: eigene Tabelle `node_nyx` (nicht `node_status`), damit Agent-Polls und Balance-Checks sich nie gegenseitig überschreiben. `set_nyx()` behält Adresse und letzte Balance bei Fehlschlag (COALESCE) und setzt nur `error`; ein Node mit totem API wird über die gecachte Adresse weiter geprüft. Eine gelesene 0 ist eine echte 0 (low), `None` heißt unbekannt (kein Warn, nur `error`).
- Zweite Quelle: nym-api-Annotation `https://validator.nymtech.net/api/v2/nym-nodes/annotation/<node_id>` (numerische Node-ID aus dem Bonded/Stake-Cache `nym_node_id`, alle 23 Nodes haben eine; DE01 = 42). Liefert `has_sufficient_tokens` (Netz-Schwelle 1 NYM, gate für den Config-Score), `is_fee_grant_grantee` und eine gecachte `on_chain_balance`. Reduziert via `parse_annotation()` in `node_nyx.net_json`. LCD-Balance bleibt primär (live + Adresse), nym-api-Balance ist nur Fallback (`balance_source`). **Feegrant unterdrückt `low`**, `insufficient` ist ein eigenes Warn-Flag unabhängig von unserer Schwelle.
- **Routing score** kommt aus derselben Annotation (`detailed_performance.routing_score.score`, 0..1; `parse_annotation` liefert zusätzlich `routing`/`config`). `annotate()` setzt `routing_low` nur bei bekanntem Score < `MAESTRO_MIN_ROUTING_SCORE` (Default 0.95). UI: roter Pill `routing N%` in der Namenszeile (`routingPill()`), Fleet-Summary-Item „Routing low". Bestehende `net_json`-Rows haben das Feld erst nach dem nächsten NYX-Check.
- Schwelle `MAESTRO_NYX_MIN_NYM` (Default 5), Intervall `MAESTRO_NYX_POLL` (Default 900s). Verdict `low` nur bei bekannter Balance < Schwelle. UI: Spalte „NYX" (sortierbar, `nyxCell()`), Betrag verlinkt auf `https://cosmoscan.com/nyx/account/<addr>`, Fleet-Summary-Item „NYX low"; der Refresh-Button triggert den Check parallel zum Agent-Poll.

## Hoster column
- `hoster.py` (orchestrator, pure, Suite `test_hoster.py`): Hoster aus dem Origin-AS der Node-IP — Hostnames sind die eigene Domain und sagen nichts. RIPEstat `network-info` (IP → ASN, Prefix) + `as-overview` (ASN → Holder), deckt alle RIRs ab. Kurzname: `KNOWN_ASNS` > Holder-Hints > bereinigter Holder; Namen bewusst identisch zu den Abuse-Providern (OVH, Hetzner, ATW).
- Tabelle `node_hoster` (eigene, wie `node_nyx`), `ip` = IP, für die aufgelöst wurde. Neu-Lookup nur bei IP-Wechsel, Fehler oder > 7 Tage (`needs_lookup`); Fehlschlag behält den alten Hoster, außer die IP hat sich geändert. Nur `is_global`-IPs verlassen die Maschine.
- `_hoster_loop` (`MAESTRO_HOSTER_POLL`, Default 3600s, 0 = komplett aus inkl. On-Change-Trigger), zusätzlich nach Node-Create/IP-Änderung als BackgroundTask; `POST /api/hoster/refresh` erzwingt alle. UI: Spalte „Hoster" (sortierbar, im Filter, Link auf bgp.tools, ASN/Holder/Prefix im Tooltip).

## Distro / OS upgrade
- Feature-Split: `distro.py` (orchestrator, pure Planung/Ranking — testbar ohne Netz), `/api/distro/*` in `app.py` (Fetch + Fanout + Rolling-Job), Agent-Actions `os_info` / `distro_upgrade` / `distro_upgrade_status` (ab Agent 0.12.0), UI-Modal `du-*`.
- **Der Upgrade läuft nie im Agent-Prozess.** Der Agent generiert einen self-contained stdlib-Runner (`render_distro_runner`, base64-JSON-Params gegen Escaping-Probleme) und startet ihn als transiente systemd-Unit `maestro-distro-upgrade` (`KillMode=process`). Treffpunkt ist ein JSON-State-File + Log unter CERTDIR — der Agent darf von apt neu gestartet oder die Box rebootet werden.
- Reboot-Verifikation ist pull-basiert: State-File bleibt auf `rebooting`; sieht `distro_upgrade_status` via `/proc/stat` btime einen Boot NACH `started_at`, prüft es Services (nym-node, Exit-Ifaces, fail2ban) und flippt erst bei grün auf `done`, sonst meldet es `verifying` und der Orchestrator pollt weiter.
- Orchestrator-Job: rolling (Semaphore, Default 1 Node gleichzeitig — das sind live Exit-Gateways, die rebooten). Unreachable ist mid-job **erwartet** (Reboot); erst >25 min Funkstille failt den Node. Cancel überspringt nur queued Nodes; laufendes apt wird nie abgebrochen.
- Dry run (`/api/distro/check`) ändert auf den Nodes nichts außer optionalem `apt-get update`. Release-Katalog live von endoflife.date mit bewusst konservativem Static-Fallback (darf hinterherhinken, darf nie ein Release erfinden). CVE-Top-5 aus den Ubuntu Security Notices, gefiltert auf ops-relevante Pakete (`OPS_PACKAGES` in distro.py); Debian bekommt nur den DSA-Link, das ist gewollt und wird angezeigt, nicht verschluckt.
- Ubuntu-LTS-Nodes bleiben auf dem LTS-Zug (nächstes LTS, nie non-LTS, nie Multi-Hop); Debian N→N+1 via sources-Rewrite. `up_to_date` heißt: kein Release-Sprung UND keine pending Packages.
- Optionales Pre-Upgrade-Backup (`backup: true` im Upgrade-Request, Default **off**): pro Node vor dem Upgrade der volle `/api/backup`-Flow (Helper `_backup_node`, geteilt mit dem Backup-Endpoint — stop/tar/restart, Download + sha256-Verify nach BACKUPS). **Backup-Fehlschlag = Node wird nicht upgegradet.**
- `recommend_actions()` in distro.py synthetisiert aus dem Dry-Run Fleet-Empfehlungen ("Upgrade N Nodes auf X, weil …"), gruppiert nach (distro, version), Urgency aus EOL-Datum + Top-CVSS + Security-Pending; `settings` darin sind die UI-Preselects (Release-Sprung ⇒ backup=True). Blockierte Nodes bekommen eine eigene "Fix first"-Empfehlung.
- **USN-API-Fakten (empirisch verifiziert, nicht raten):** `notices.json` cappt `limit` hart auf **20** (422 darüber) → Offset-Pagination; die Liste trägt **keine Severity** (leere `cves`, IDs in `cves_ids`, `cvss3`/`priority` null) — CVSS kommt nur vom per-CVE-Endpoint `cves/<id>.json` (gecappte Anzahl Fetches, dann `rescore_with_cves`). Ops-Match nur auf **Source-Pakete** (`is_source`), sonst zieht `python3-samba` Samba in den Python-Bucket.
- **BE01-Incident (2026-08-19), eingebaute Lehren:** Tatsächliche Ursache war ein **systemctl-False-Negative** — `systemctl is-active` schlägt mid-release-upgrade transient fehl (systemd/dbus werden gerade selbst upgegradet), der Runner lief die ganze Zeit weiter. Deshalb gilt zuerst: **State-File-mtime < 120s = Runner lebt** (`_distro_state_fresh`, systemd-unabhängig; run_stream schreibt ~alle 2s), erst danach die Unit-/Lock-Evidenz. Zusätzlich abgesichert (plausible Nachbar-Failure-Mode): needrestart (via `NEEDRESTART_MODE=a`) könnte die transiente Runner-Unit selbst "restarten" → Runner tot, apt/do-release-upgrade-Kind läuft dank `KillMode=process` weiter. Deshalb außerdem: (1) needrestart-Pin nach `/etc/needrestart/conf.d/zz-nym-maestro.conf` vor jedem Start, (2) Runner-Kind schreibt stdout DIREKT ins Log-File (nie Pipe — toter Reader würde das Kind blockieren), Progress via Log-Tail, (3) `distro_upgrade_status` entscheidet bei toter Unit nach Evidenz: apt-Lock gehalten ⇒ Phase `detached` (weiterwarten); Lock frei + `VERSION_ID` ≠ `from_version` ⇒ verify ⇒ `done` mit Note; sonst failed. `verify`-Checks haben `gate: False` für Nicht-Outage-Checks (z.B. "sudo installed" — Ubuntus sudo→sudo-rs-Transition kann sudo fressen; Runner-`ensure_essentials()` installiert sudo/openssh-server nach Release-Sprüngen nach).

## Extra blocks / blocklist (NYM-EXIT)
- Drei Dinge im selben Oneshot `nym-extra-blocks` (PartOf/WantedBy nym-node, `sleep 10`), alle in `filter NYM-EXIT`: (1) Scan-Rate-Limit `nym_scan_v2` (200/sec, burst 1000, `-j DROP`) — **maestros eigene Regel**, eingeführt mit da60ac6 (2026-09-30). Nyms `network-tunnel-manager.sh` (develop, geprüft 2026-11-19) bringt **kein** Scan-Limit mit, nur `smtps465v4/v6` für Port 465 — nicht entfernen in der Annahme, NTM übernehme das. (2) Fan-out-Limiter (eigene Sub-Chains). (3) Blocklist.
- Blocklist: maestro ist Source of Truth (`app_config` Key `blocklist`, Text wie editiert, einmalig aus dem Repo-`blocklist.txt` geseedet). `blocklist.py` (pure) validiert — strict CIDR (Host-Bits = Fehler mit Hinweis), zu breite Prefixe (< /16 v4, < /32 v6) abgelehnt; `agent.eb_canonical` muss identisch entscheiden (Paritätstest). Kein GitHub-Fetch mehr, kein `list_url`, kein „Run installer".
- Rollout (`POST /api/extra-blocks/install`) schickt die **gespeicherte** Liste als `entries`; Agents < 0.12.9 werden übersprungen (sie würden `entries` ignorieren und von GitHub laden). Script reconciled: alle `--comment nym_block`-REJECTs per exakter Spec drainen, dann Liste markiert oben einsetzen. Migration: ungemarkerte Alt-REJECTs exakter Altform nur für Ziele aus aktueller Liste ∪ `legacy.txt` (= alter Cache, einmalig beim ersten Install gesichert) — fremde Policy-REJECTs werden nie angefasst.
- Status: `blocked_count` = markierte Regeln der Liste, `stale_rules`, `legacy_rules`, `hits` (+ `hits_per_dest` im Modal), `list_sha` (gleich `blocklist.list_sha` → UI-Flag „list outdated"), `rate_limit_rules` (> 1 = gestapelt).
- `install-nym-extra-blocks.sh` ist nur noch eine aus dem Template generierte Standalone-Kopie (wortgleich, Test prüft es).

## Nym concurrency (anti-BitTorrent)
- Per-Client-Cap auf **gleichzeitige** Verbindungen zu High-Ports (12000–65535, TCP+UDP) via `connlimit` in eigener Chain `mangle NYM-CONCURRENCY`, gehookt aus PREROUTING **nur** für `-i nymwg`/`-i nymtun0`. Unabhängig von Extra-Blocks (filter/NYM-EXIT: `nym_scan`-Rate + Fan-out begrenzen, wie *schnell* ein Client Verbindungen öffnet; das hier, wie *viele* er hält). Kalibrierung: legit ≤26, Torrent 279–670 → Default-Limit 50.
- Nur `--ctstate NEW` wird geprüft (bestehende Flows nie gedroppt, Per-Paket-Pfad billig). v4 `--connlimit-mask 32`, v6 `128` (= pro Client-Adresse, das Limit bleibt dasselbe), v6 best-effort. TCP und UDP zählen getrennt.
- Template `NC_SCRIPT`/`NC_UNIT_TPL` in agent.py ist Source of Truth; `install-nym-concurrency.sh` (Standalone, wird von maestro NICHT ausgeführt) muss wortgleich bleiben — `test_concurrency.py` prüft das. Limit steht in `/var/lib/nym-concurrency/limit` (nie im Script-Text), validiert 10..10000 in Script, Agent und Orchestrator.
- Script: Chain erst bauen, dann hooken; Hooks per exakter Spec drainen (auch der unscoped Hook der manuellen Test-Installation); bei v4-Fehler kompletter Teardown + Exit 1 (fail-open, sichtbar). Unit hat `ExecStop=… stop`, `PartOf`/`WantedBy` nym-node.
- Agent-Actions `concurrency_{status,install,set_limit,restart,verify,remove}` (ab 0.12.8), Status-Poll-Feld `concurrency` → Spalte `node_status.concurrency_json`. Limit/Drops werden live aus `iptables -L -x` gelesen (`#conn src/32 > N`), nie aus der Config. Drop-Counter = Pakete, Reset bei jedem Re-Apply (`since`).
- Orchestrator `/api/concurrency/*`: install/limit/restart nur auf Exit-Gateways (`landing.is_exit_gateway`), status/verify/remove auf allen (Aufräumen).

## Versioning
- Agent-Version steht auf **0.12.9** (`AGENT_VERSION` in `agent/agent.py`; 0.12.0 = Distro-Upgrade-Actions, 0.12.1 = Upgrade-Resilienz: needrestart-Pin, Orphan-Recovery, ensure_essentials, 0.12.2 = State-Freshness als Liveness-Signal + `_distro_reconcile` auch im os_info-Summary, damit ein stuck Mid-Flight-State per Scan self-healt statt Upgrades zu blocken, 0.12.3 = reset-failed vor Service-Restart, 0.12.4 = adaptiver Restart-/Stop-Wait, 0.12.5 = Fan-out-Limiter-Status (`fanout_*` im extra_blocks-State: Hook in NYM-EXIT + REJECT-Counter aus NYM-FANOUT-NEWDST, Reset bei jedem Oneshot-Lauf), 0.12.6 = Fan-out-Limiter auch in der Built-in-Vorlage `EB_SCRIPT`, damit Upgrade/Install ihn erhalten — Config + `fanout_apply` müssen mit `install-nym-extra-blocks.sh` wortgleich bleiben, Test 17b prüft das), 0.12.7 = `os` (aus /etc/os-release) im Status-Poll für die OS-Spalte der Node-Tabelle; ältere Agents fallen orchestrator-seitig auf den letzten Distro-Scan zurück), 0.12.8 = nym_concurrency (connlimit gegen BitTorrent, `concurrency_*`-Actions + `concurrency` im Status-Poll), 0.12.9 = maestro-verwaltete Blocklist (`entries` statt `list_url`, `nym_block`-Marker, Reconcile + Migration, Hits/list_sha/stale/legacy im State).
- **Service-Restart-Wait (`_restart_service`/`_stop_service`):** 150s Soft-Budget, bis 420s Hard-Cap, aber nur solange `ActiveState=deactivating`. Grund: Exit-Gateways mit ~15k WireGuard-Peers blocken beim Abbau von `nymwg` minutenlang uninterruptible im Kernel — SIGKILL greift erst, wenn der Kernel zurückkommt ("Processes still around after SIGKILL. Ignoring."); AT01 brauchte 4:08 min von "Stopping" bis "Started", danach lief alles. Ein Unit, das `active`/`activating` nie verlässt, läuft weiterhin nach 150s in den Timeout. Orchestrator-Timeouts dazu passend: exec restart/toggle 480s, upgrade 900s, backup 1500s. Node-seitige Ursache ist nicht maestro-fixbar (nym-node/Kernel-WireGuard).
- Vor Annahmen über Feature-Verfügbarkeit fleet-weit den Agent-Versionsstring prüfen — nicht alle 23 Nodes laufen zwangsläufig auf derselben Agent-Version.
- Es gibt keine Capability-Negotiation: ein alter Agent antwortet auf eine unbekannte Action mit HTTP 400 `unknown action: ...`. Das ist das Feature-Detection-Signal. Achtung: `agent_exec` macht `raise_for_status()`, und httpx' Exception-Message enthält den Response-Body NICHT — für eine brauchbare Fehlermeldung `e.response.json()["error"]` auslesen (siehe `_landing_fanout`).

## Working conventions
- **Der echte SSH-Login-User steht NIRGENDS im Repo** (Code, Kommentare, Tests, Docs) — er kommt ausschließlich aus `MAESTRO_SSH_USER` (Orchestrator-Env beim Start via `run.sh`, Agent-Env in der Unit). Ohne gesetzte Variable sind die SSH-Aktionen funktionslos (verify baut dann `ssh @host` → Usage-Dump). Bei neuen Features/Tests neutrale Namen verwenden.
- Bei allem, was mTLS/Cert-Logik betrifft oder Agents fleet-weit offline nehmen könnte, vorher nachfragen — ein Bug hier heißt nicht "Commit reverten", sondern "22 Nodes melden sich nicht mehr."
- Defensiver, expliziter Code auf Agent-Seite (keine externen Error-Handling-Libs — stdlib only, siehe oben).
- Beim Hinzufügen von Orchestrator-API-Feldern/Endpoints auf das Muster achten, das im Schwesterprojekt SOZU bereits aufgetreten ist: still fallengelassene Felder in Config-APIs. Verifizieren, dass neue Felder tatsächlich durchverdrahtet sind, nicht nur deklariert.
- Fleet hat heterogene Node-Historie — im breiteren Nym-Ops-Kontext gab es NAT/Routing-Eigenheiten (IPv6 NAT66, verwaiste WireGuard-Peer-States) auf einzelnen Nodes. Nicht direkt Aufgabe dieses Repos, aber bei verdächtigem Reporting für einen einzelnen Node ein plausibler erster Verdacht.

## Testing
- Vor "fertig" die Test-Suites für Agent und Orchestrator laufen lassen. Existiert für ein geändertes Modul noch keine Test-Suite, das explizit benennen statt die Verifikation stillschweigend zu überspringen.
- Für Agent-Änderungen: da stdlib-only, Tests nicht mit Third-Party-Test-Deps überladen, die nicht schon etabliert sind (pytest als Dev-only-Dependency ist unkritisch, wird ja nicht auf die Nodes ausgeliefert).
- **Die Suites sind Skripte, nicht pytest-Tests** — direkt laufen: `.venv/bin/python test_<name>.py`. Jede printet `N passed, M failed` und exitet mit 1 bei Fehlern. Vorhanden: `test_actions`, `test_agent_mtls`, `test_delegation`, `test_extra_blocks`, `test_concurrency`, `test_blocklist`, `test_hoster`, `test_landing`, `test_migration`, `test_nyx`, `test_peers`, `test_wallet`, plus `smoke_test.py`.
- `test_wallet.py` hat einen bekannten, vorbestehenden Failure (`redeem passes --mnemonic`) — nicht durch neue Änderungen verursacht, vor dem Debuggen gegen HEAD verifizieren.
- `test_agent_mtls.py` enthält das Harness, um einen echten Agent lokal mit frischer CA + Enrollment über echtes mTLS zu starten (`pki.init_ca` / `pki.enroll` + Subprocess). Für Wire-Level-Tests neuer Agent-Actions von dort kopieren, statt nur `act_*` in-process aufzurufen.

## Git / commits

- Orchestrator- und Agent-Änderungen nicht in einem Commit bündeln, außer sie sind wirklich gekoppelt (z.B. eine Wire-Protocol-Änderung zwischen beiden).
